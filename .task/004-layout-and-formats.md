### L layout crate (after S1; files only in `layout/`)
Port of ngraph.forcelayout 3.3.1 as `rust-engine.ts` (`startLayout`/`stepLayout`) and `build-similarity.mjs` call it; read from `node_modules/ngraph.forcelayout` source. Dimensions 3; body mass `1 + degree/3`; forces in order nbody then spring; nbody = Barnes-Hut octree with `gravity` -2.5 (Coulomb) and `theta` 0.9; spring = Hooke, rest length per spring, coefficient `springCoefficient` 0.0008, force `coeff * (r - length) / r`; drag `-dragCoefficient * v` (0.04); integrator `v += (timeStep/mass) * force`, if `|v| > 1` then `v = v/|v|`, `pos += timeStep * v`, timeStep 20; the callers then multiply positions by 0.99 after each step (a pull to the origin, kept as `Params::centring`, 1.0 = off; `build-graph.mjs` has none). Rest length per link comes from the caller (`springTransform`): similarity maps `17.5 + (1 - t) * 30`; graph.json maps `[20,30,45,60,60][type]`.
FINDING: `springTransform` also sets `spring.weight` (0.6 + 0.4t; [1,0.7,0.4,0.3,0.3]) but ngraph 3.3.1's spring force never reads it (only `spring.length` and `spring.coefficient`; `Spring` has no `weight`). The committed positions were produced with a constant coefficient. The port reproduces the effective behaviour: links carry a rest length only. See Q2.
Determinism: ngraph seeds `ngraph.random(42)`, used only to split coincident bodies (`(rand - 0.5)/50`). Rust: a seeded splitmix64 (no `rand`: wasm32 and MSRV stay trivial), same use. Internal f64 (as JS), f32 out for the engine.
**Parity method (point 1): trajectory comparison against committed ngraph fixtures within a tolerance; NOT bit equality** (other PRNG stream, other float summation order). Probe (Node, 300 nodes, two clusters, ngraph 3.3.1, the real parameters): the layout is not chaotic: two identical runs differ by 0, and a 1e-9 perturbation of the start stays 1e-9 after 1 step and 2.7e-11 after 400 (radius of gyration 91 at step 1, 350 at 400). L2 compares Rust to fixtures (generator `layout/tests/fixtures/gen.cjs` + its JSON output, generated once; Node goes in 008, the fixture stays) at steps 1, 5, 20, 400 on a 300-node two-cluster graph with the similarity springs and `centring 0.99`: per-node max distance <= 1e-3 at steps 1 and 5, <= 1% of the radius of gyration at 400, radius of gyration within 1%. If the octree build order differs so that 1e-3 cannot hold, the fallback, stated now: a statistical comparison (radius of gyration, mean spring length per rest-length class, inter-cluster distance within 3%, over 5 starts); taking it needs `@orchestrator` (weaker test).
- L1 `layout/src/{lib,params,prng,body,octree,forces,integrate}.rs` (lib.rs only declares and re-exports). Tests first, in each file: `same_seed_same_positions`; `coincident_bodies_split` (r == 0 gives no NaN); `two_clusters_separate` (two 50-node cliques joined by one link, interleaved start: mean intra-cluster distance < 0.5 x centroid distance after 400 steps); `energy_falls` (movement returned by `step`, like ngraph's totalMovement, smaller at step 400 than at 20); `octree_matches_brute_force` (theta 0.9 within 5% per body, 200 bodies; theta 0 equal to 1e-9); `spring_pulls_to_rest_length`; `drag_opposes_velocity`; `velocity_capped_at_one`; `centring_scales_positions`; `empty_graph_and_isolated_nodes`; `rejects_link_to_missing_node` (a Result, never a panic: the wasm module aborts on panic). Every public item documented.
- L2 `layout/tests/ngraph_parity.rs`, `layout/tests/fixtures/{gen.cjs,small.json}`. Test first: the parity test itself, red until L1's numbers are right.
- Performance: 7286 nodes, ~25k links, 400 steps within the engine's 14 ms slices: a host timing in an `#[ignore]`d test, quoted not gated (A4).

### F formats crate (after S1; files only in `formats/`; deps: serde, serde_json; wasm32-clean)
Reader today (`src/map/data.ts`): graph files `{legendTitle?, colors?, types[], langs[{iso,name}], pitakas[], collections[{uid,name}], nodes[], edges[], sim?, fixed?}`; `NodeRow = [uid, acronym, en, root, coll, group, pitaka, x, y, z]` (10-array: 4 strings, 3 indices, 3 numbers: integers in graph/graph-sim, 1 decimal in pca/umap/tsne); `edges` flat `[a,b,type,...]` (19839 values in graph.json, empty in the sim family); `sim? = {url, min, max, default, range?[lo,hi]}`; `fixed?: true` in pca/umap/tsne.
**`graph-sim.bin` layout (point 2)**, quoted from `loadPairs`: `const n = buf.byteLength / 6; ... p.a[k] = buf.getUint16(k * 6, true); p.b[k] = buf.getUint16(k * 6 + 2, true); p.sim[k] = lo + (buf.getUint16(k * 6 + 4, true) / 65535) * (hi - lo);` with `[lo, hi] = sim.range ?? [0, 1]`. Writer (`build-similarity.mjs`): `writeUInt16LE(a, k*6); writeUInt16LE(b, k*6+2); writeUInt16LE(Math.round(clamp((s - lo)/(hi - lo), 0, 1) * 65535), k*6+4)`, pairs sorted by similarity descending, a < b, N <= 65535. So: no header, no footer, little-endian records of 3 x u16 = 6 bytes; the committed file is 556668 bytes = 92778 records exactly (checked). Any header or trailer breaks today's reader (`n` becomes fractional, the loop reads past the buffer), so the .bin cannot carry a stamp.
**Stamp placement (point 3)**, valid while the React reader lives (until 008):
  - `graph.json`, `graph-sim.json`, `graph-sim-{pca,umap,tsne}.json`: a top-level `"stamp"` key. The reader types `Graph` and reads named keys; nothing iterates a graph's keys (grep: no Object.keys/entries on a graph); `reduce-3d.py` copies unknown keys (`dict(base)`), so the vectors sha flows into the three reduced files.
  - `graph-sim.bin`: no stamp in the file; `sim.sha256` (digest of its bytes) in `graph-sim.json`'s `sim` object (read key by key, an extra key is harmless); the data check ties bin and JSON.
  - `translations.json`, `blurbs-{en,fr}.json`: NOT inline. `translations.json` is iterated by `Object.entries(translations)` (`src/App.tsx:277`, reading `tr.titles` of each entry), so a `"stamp"` key would throw at runtime; `blurbs-*.json` is a uid map (the key would be a fake uid). They are stamped by a sidecar `public/stamp.json` = `{ files: { "<name>": { sha256 } }, sources: [{ name, commit }], vectors_sha }`. Q1.
  - `Stamp` type: `{ sources: Vec<SourceCommit { name, commit }>, vectors_sha: Option<String> }`; 007's data check compares `vectors_sha` across the sim family.
- F1 `formats/src/{lib,graph,stamp}.rs`, `formats/tests/graph_files.rs`: `NodeRow` with a hand-written serde (10-tuple), `Graph`, `SimInfo`, `Stamp`. Tests first: `node_row_round_trips`, `node_row_wrong_length_errors`, `graph_without_stamp_parses`, `graph_with_stamp_parses`, `unknown_key_is_kept_not_rejected` (pins forward compatibility); integration `public_graph_files_parse` (graph.json 3305 nodes; graph-sim and the three reduced 7286; `edges.len() % 3 == 0`; every edge index < nodes; `coll`/`group`/`pitaka` indices in range) and `sim_family_shares_node_set`.
